## 一、① 必需试剂判据

### 1.1 口径（写死，避免重测）

- **覆盖率** = 该类反应里用了该试剂的比例；**分母 = 成功归类到 37 类的反应数**（不是扫描条数）。
- **扫描范围**：前 400,000 条（全量 1,771,032 条的 22.6%）→ 归类成功 **81,444 条 / 33 类**。
- **必需件**：个体覆盖率 ≥ **0.50**，且该类样本 ≥ **20** 条（否则不敢判零）。
- **角色归并**：同功能分子（DEAD+DIAD、NaBH4+NaBH3CN、Et3N+DIPEA…）覆盖率**相加** ≥ 0.50 也算必需件。
  SMARTS 表在 `core/smartreact_engine.py: REAGENT_ROLE_SMARTS`，共 6 个角色。
  ⚠ **这是建模选择（我的化学判断），不是 ORD 实测值**；它只决定「哪些实测覆盖率可以相加」。
- **判据语义**：条件里**没写试剂 → 不检查**（向后兼容）；写了试剂但缺任一必需件 → **判零 0.0**。

### 1.2 实测结果

**有硬性判据的类：5/37**

| 反应类型 | 样本 | 必需件（角色，覆盖率，成员数） |
|---|---|---|
| `mitsunobu` | 1831 | phosphine 59%(1) + **azodicarboxylate 51%(2)** |
| `reductive_amination_aldehyde` | 4182 | borohydride 61%(2) |
| `reductive_amination_ketone` | 1165 | borohydride 56%(2) |
| `suzuki` | 8015 | carbonate 56%(1) |
| `ester_sulfonic_schotten_baumann` | 2103 | trialkylamine 54%(1) |

**场景实测**（`tools/test_required_reagent_gate.py`）：

| 场景 | 判定 |
|---|---|
| Mitsunobu 只给 PPh₃ | **判零**：缺 azodicarboxylate(51%) |
| Mitsunobu PPh₃ + DEAD | 1.00 |
| Mitsunobu PPh₃ + DIAD（等价物） | 1.00 ← **不误杀等价物** |
| Mitsunobu 只给无关试剂 | **判零**：两个都缺 |
| Mitsunobu 一个试剂都不写 | 1.00 ← 向后兼容 |
| Suzuki 给了无关试剂 | **判零**：缺 carbonate(56%) |
| 还原胺化 只给 Et₃N | **判零**：缺 borohydride(61%) |
| 还原胺化 给 NaBH₃CN | 1.00 |
| **37 类 × 不写任何试剂** | **37/37 全部放行**（回归断言，通过） |

**在真实底物上的效果**（12 个中药成分，`tools/test_reagent_gate.py`）：
煎煮 100°C **+ PPh₃** 时产物 17 → **12**，`reductive_amination_*` 被正确拦掉
（写了 PPh₃ 却没写还原剂 → 还原胺化判零）。

### 1.3 三个必须先修的坑（都是实测发现，不修则判据是错的）

1. **立体化学把同一个试剂拆成两个桶**（最贵的一个）
   实测 10 万条：DEAD 写成 `CCOC(=O)/N=N/C(=O)OCC`（有立体）111 条 + 无立体 121 条
   → 保立体下是**两个不同试剂**，各占一半覆盖率；DIAD 同理 67+69。
   PPh₃ 没有立体，所以一直是正常的 59% —— 这就是「59% vs 18%」的真正原因
   （**我一开始的假设是错的**：原以为 DEAD 写在 CXSMILES 的 agents 段被口径忽略，
   实测 agents 段里 azo 只有 **1** 条，phosphine 也只有 1636/3664 —— 假设被数据否定）。
   → 修：覆盖率与判据的 canonical 一律 `isomericSmiles=False`。
2. **离子碎片被当成必需试剂**
   CXSMILES 把 K₂CO₃ 拆成 `O=C([O-])[O-]` + `[K+]`。
   修复前的 required 里 `[Na+]` 出现 **13** 处、`[K+]` **11** 处、`[Cs+]` **6** 处 —— 若不剔除，
   会出现「缺 K⁺ 判零」这种荒谬判据。→ 修：单原子碎片一律不算必需件。
3. **别名表两处手写 SMILES 是错的**（AGENTS.md 第三条「不要手写数据」的活案例）
   | 键 | 原值 | 分子式 | 正确结构 |
   |---|---|---|---|
   | `hobt` | `O=Nn1nnc2ccccc21` | C₆H₄N₄O（苯并三唑 N-氧化物） | `On1nnc2ccccc21`（C₆H₅N₃O） |
   | `dcc` / `dicyclohexylcarbodiimide` | `N#CN=C1CCCCC1` | C₇H₁₀N₂（异腈-亚胺） | `C1CCCCC1N=C=NC1CCCCC1`（C₁₃H₂₂N₂） |
   以前只是"匹配不上→降权"，现在会**判零**，别名错就是**误杀**。已改正，核对脚本 `tools/probe_reagent_roles.py`（13 例 0 存疑）。
4. 附带修：**组分级匹配**。调用方给的 `K2CO3` 是整分子 SMILES，表里存的是碎片
   → 整串比较必然不等 → 误判"缺试剂"。现在整串相等**或任一组件相等**都算命中。

### 1.4 局限（说清楚，别当成完备）

- 覆盖率**只统计 CXSMILES 的 reactants 段**（沿用 `build_condition_table.py` 的口径，
  该口径原本就是「声明为 REACTANT 但原子没进产物」）。agents 段的试剂不计入。
  实测影响：azo 在 agents 段几乎不存在（1/200000），phosphine 1636 vs 3664 —— 对这两类影响有限，
  **对只写在 agents 段的试剂仍会低估**。这是下一步要改口径的地方。
- 只跑了 40 万条（前 8 片）。续跑到全量：`python tools/run_aux_reagent_coverage.py`
  （已支持**跳过已完成分片**；8 进程一片 5 万条约 6.5 分钟，剩 28 片）。
- 阈值 0.50 / 样本 ≥20 是**拍的**（建模选择）；`amide_coupling`（HATU 18%、HOBt…）等
  "缩合剂可选"的反应因此拿不到必需件 → 不判零（保守，宁漏勿杀）。
- 角色 SMARTS 只覆盖 6 个角色；表外的试剂只能按单分子 ≥0.5 判。

## 二、② 扩溶剂词表

### 2.1 词表

`conditions/model.py` 现在是**双层**：6 个粗类别（water/aqueous/alcohol/oil/none/organic）
+ **26 个细类别**（thf / dcm / dmf / toluene / mecn / dioxane / et2o / etoac / dmso / nmp / dma /
dme / chcl3 / dce / pyridine / et3n / dipea / acoh / nh4cl / pocl3 / hexane / benzene / acetone /
methanol / ethanol / isopropanol）。别名表 60+ 写法。

**匹配规则**（`conditions/model.py: solvent_matches`）：
同名匹配；任一边是粗类别且父类相同 → 匹配；**两边都是细类别且不同 → 不匹配**（新增的区分力）。

### 2.2 实测（`tools/test_solvent_gate.py`）

| 指标 | 旧 | 新 |
|---|---|---|
| ORD 溶剂写法被词表认识 | —— | **26/26（无静默兜底）** |
| 37 类中偏好溶剂被压成单一类别（区分力=0） | **8/30** | **2/30** |
| 能按 ≥2 个细类别区分的类 | —— | **28/30** |

**回归**（把旧 `_solvent_class` 逻辑抄进测试当参照，13 例逐条比对）：**断言 0 失败**。
其中一处是**有意改正**：`alcohol` vs ORD `['MeOH']` 旧=False（粗类别被细类别判死）→ 新=True。

### 2.3 接线与验收

- `core/smartreact_engine._solvent_class` 改为**委托** model（单一真相，不再两处维护）；
  溶剂门控改用 `solvent_matches`。
- `conditions/activator.SOLVENT_FAMILY` 改为**从 `SOLVENT_PARENT` 生成**（原来只硬编码 3 条）。
  不这么做，用户写 `thf`/`DMF` 会让 64 条手工规则全部命中「不在 allowed → 0」，把整条正向链判死。
- 验收：`test_conditions.py` **20 通过 / 0 失败**；`test_condition_gate.py` 数字与上一轮**完全一致**
  （室温水浸 16 / 煎煮 11 / 乙醇 16 / 高温久煎 1；煎煮仍正确拦掉 mitsunobu）；

## 三、③ 反例数据

### 3.1 先把 ORD 翻干净：它没有负例字段

逐字段读 DESCRIPTOR（不猜）：

- `Reaction` 没有「失败/没反应」字段；`ReactionNotes` 只有
  `procedure_details / safety_notes / is_exothermic / offgasses …`。
- `ReactionOutcome.conversion` **在这份数据里从未被填过**：0 / 100,000。
- 这份 `ord_schema` 的 `ReactionInput` **连 reaction_role 字段都没有**，inputs 的 key 是
  `m1_m6_m2_m7_m3` 这种机器名 → 「角色」只能从 CXSMILES 段位推断。

### 3.2 收率字段要先排雷（差点把假反例当宝贝）

`yield == 0` 命中 61/100,000 —— 抽出来看原始记录，全是 **`details=CALCULATEDPERCENTYIELD`**
（计算收率 0），同一记录的 `PERCENTYIELD` 是 **27.5% / 25.0%**。
全量核实：**真实 PERCENTYIELD==0 有 404 条，CALCULATEDPERCENTYIELD==0 有 405 条** → 必须按 `details` 区分。

### 3.3 抽出来的候选（全量 1,771,032 条，扫描 213 秒）

| 路线 | 口径 | 条数 | 文件 |
|---|---|---|---|
| **A 文本** | notes 命中**严格否定短语**（no reaction occurred / no conversion / did not react / failed to react\|give / no product formed / starting material recovered / reaction did not proceed…） | **449** | `reports/negative_examples.jsonl` |
| **B 收率** | 真实 `PERCENTYIELD == 0`（排除 CALCULATED） | **404**（其中**全零 229**、有非零收率 175） | `reports/negative_yield_zero.jsonl` |

**A ∩ B = 0** —— 两条路线完全不重叠，合起来 **853 条**（占全量 **0.048%**）。
A 路按短语拆开：sm_recovered 83 / no_reaction 72 / reaction_did_not_proceed 67 /
unreacted_remaining 64 / failed_to_react_or_give 57 / no_product_formed 47 / no_conversion 33 /
not_consumed 15 / did_not_react 13。
（宽松词 `trace` 211、`decompos` 733 已**剔除**：抽看上下文几乎全是噪声。）

### 3.4 人工复核精度（我逐条看的，12 条抽样，seed=20261011）

| 类别 | 条数 | 例子 |
|---|---|---|
| **严格反例**（该条件下确实没反应/没产物） | **2** | 「After 12 h, as no product was detected, sodium borohydride was added」；「TLC … the starting material which did not react」 |
| **弱反例**（部分转化 / 补加试剂后才推进） | **5** | 「TLC indicated the reaction did not go to completion」（随后补催化剂）；「HPLC … did not go to completion (86% conversion)」 |
| **假阳性** | **5** | 后处理描述（「extracted until no product was observed in the water layer」）；某组分未消耗（「some of the zinc powder remained unreacted」）；原料回收但有 24% 产物 |

→ **严格反例精度 ≈ 2/12 = 17%**（样本小，置信区间很宽）；
把弱反例也算上 ≈ **7/12 = 58%**，但弱反例只能支持「该条件不充分」，不能当「不反应」用。

### 3.5 结论（我的判断）

- **从「完全没有」推进到「有 853 条可复现的候选 + 精度已量化」**，流水线可重跑、口径写死。
- **但仍不足以算假阳性率**：严格反例估计只有 ~17% × 853 ≈ **百余条**，且彼此不同反应不同条件，
  够做「抽查式误报检查」，不够做统计意义上的 FPR。
- 下一步该做的是**把 853 条筛成"干净反例集"**（人工/LLM 逐条判，估计 1~2 小时），
  然后才谈「在反例上跑正向引擎 → 预测了不该发生的反应 = 假阳性」这个真正的指标。
