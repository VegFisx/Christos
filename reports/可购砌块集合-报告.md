## 一、这一轮到底做了什么

上次会话停在「①做可购砌块集合 还是 ②提高逆模板质量」，用户选 **①**。

**问题**：逆合成现在的终止集合是 COCONUT(27.3万) + tcm.db(2.9万) = **天然产物**，
不是**化学家能买到的原料**。上次逆合成能跑通，只是因为乙酸/酪胺/水杨酸恰好都在 COCONUT 里。

**做法**：从 ORD 里取「**只作为反应物出现、从不作为产物出现**」的分子 = 化学家买来的砌块。

---

## 二、口径（先说清再测）

| 项 | 定义 |
|---|---|
| 数据源 | `ord_data/data/11/ord_dataset-1158e351757f315b93cbcbe7bc55f38e.parquet`（**实测**：1,771,032 条，是 53 个 parquet 里**唯一**带 CXSMILES 的文件；其余 52 个各抽 200 条，CXSMILES 命中 0） |
| 入账范围 | CXSMILES 的**反应物段**与**产物段**；**中段（agents/溶剂）不入账** |
| 分子切分 | 按 `.` 拆单组分（盐/水/多组分各算独立分子） |
| 分子身份 | RDKit **去原子映射后**的 canonical SMILES（`SetAtomMapNum(0)` 再 canonical，保留立体与电荷） |
| 砌块判定 | 在反应物段出现过 **且** 在产物段从未出现 |
| 计数 | 逐反应计数，同反应同侧同分子只计一次（去重，不含化学计量数） |

**★ 关键区分（不区分就会把试剂当砌块）★**
"反应物有、产物没有"里面既有真砌块（胺/酸/醛/卤代物），也有**试剂/催化剂**
（NEt₃、DIPEA、[H⁻]、DMF、THF…）。判据用**映射率**：

> 映射率 = 该分子作为反应物时【带原子映射号】的次数 / 总次数
> - 带映射 → 它的原子进了产物 → **真底物（砌块）**
> - 不带映射 → 只是条件试剂/溶剂/催化剂 → **不是砌块**

因此拆成两个文件：
- `purchasable_blocks_core.tsv` = 映射率 ≥ 0.5 且 带映射次数 ≥ 5 → **核心砌块**
- `purchasable_blocks_reagents.tsv` = 其余 → **试剂/溶剂/催化剂**

## 四、①到底有没有用？（受控评估，实测）

口径：目标 = ORD 真实反应的**产物**（MW ≤ 500、单组分），抽样 160 个（固定种子）；
切断方案 = 9,770 条反转模板（与 retro_search 同一套）；只算一次，两组共用。

| 终止集合 | 一步到位 | 比例 |
|---|---|---|
| A 旧（COCONUT + tcm.db） | 2 / 160 | 1.2% |
| B 旧 + ①砌块 | **8 / 160** | **5.0%** |
| **净增益** | **+6** | **+300%（相对）** |

- 仅 B 能解决 **6** 个；仅 A 能解决 **0** 个 → **没有任何损失，只有增加**
- 例：`Brc1ccc2c(c1)CC2`（溴代茚满）、`COc1c(Br)cccc1[N+](=O)[O-]`、
  `OCCCCCc1ccc2c(c1)OCCO2` 等——**旧集合里根本没有这些简单砌块**

**★ 但必须看清的分母**：加了砌块也只有 5.0%。说明
**终止集合不是主要瓶颈，逆模板质量才是**（①是必要条件，不是充分条件）。
这正好是选项②要解决的问题。

## 六、已知问题（必须知道，别当成干净的）

1. **互变异构体被当成不同分子**（实测，41/30,000 = 0.14%）
   身份用 canonical SMILES，RDKit 把互变异构体视为不同分子，而 InChI 会归一化。
   所以 E 自检在 full InChIKey 层面复现出 41 个"砌块又出现在产物侧"，
   其中 39 个是互变异构体、12 个 canonical SMILES 完全相同、2 个是立体异构。
   → **影响很小，但没有消除**。若要严谨，可改用 InChI 归一化身份重做（代价：一次重跑）。
2. **同一反应两侧出现同一分子 = 5.54%**（实测 1,108/20,000）
   ORD 数据本身的质量问题。这类分子会同时进 R 和 P，因此**不会**被误判成砌块（保守方向）。
3. **中段（agents）完全没入账**（有意为之）
   中段里的分子可能是真试剂；代价是某些"其实是造出来的"分子被当砌块，方向偏保守。
4. **InChI 会挂死 —— 已定位并解决**（实测）
   - 现象：第一次全量跑卡在「计算砌块 InChIKey 282,000/297,885」不动，
     CPU 100% 持续占用（实测：6 秒内消耗 5.91 秒 CPU）→ RDKit 的 InChI **死循环**，不是 I/O 等待。
   - 原因：进程池模式下，一个 worker 卡在 C 层死循环 → `future.result()` 永久阻塞 → 整个进程池挂死。
   - 修法：`inchi_keys_with_timeout()` 改**线程池 + `as_completed(timeout)`**，
     单批超时 30~120 秒就跳过并记账，卡住的线程不再阻塞主场。
   - **验证**（`tools/diag_inchi_hang.py`，30 秒/批）：对全部 **297,885** 个砌块重扫，
     **完成 297,885、挂死 0、耗时 104 秒** → 现行代码路径下不再有分子触发死循环。
     结论标注：**实测**。
5. **只用了 1 个 parquet**（53 个里唯一带 CXSMILES 的）
   "其余 52 个无 CXSMILES"是**抽前 200 条**得到的，不是全表扫描。

## 七、能否接进 TCMAI？（2026-10-11 评估，实测）

**结论：技术接入成本极低，但【现在不要正式接入】，建议做"影子接入"。**

### 7.1 接入成本（实测）

| 项 | 情况 |
|---|---|
| 逆合成的额外依赖 | **只有 `smartreact`**（纯 Python，约 100 KB + 模板数据） |
| rdkit | TCMAI 的 venv 里**已有 rdkit 2026.3.6**，不用动 |
| chemreact-staging\libs | **487 MB，但基本不需要**（里面 90% 是 IPython/jupyterlab/metaflow 等无关包） |
| TCMAI 现状 | tkinter 单窗口（`launcher.py` 276 行，只 import llm_agent）+ PyInstaller |

→ **"接不进去"不是问题，问题在质量。**

### 7.2 逆合成在【中药成分】上的实测（80 个 tcm.db 成分，MW 200~600）

| 指标 | 值 |
|---|---|
| **一步到位**（全部前体都是已知终端） | **12/80 = 15.0%** |
| 部分前体可得 | 64/80 = 80.0% |
| 有切断但前体全都不可得 | 4/80 = 5.0% |
| 无切断方案 | 0/80 = 0.0% |

**注意：15% 不能和第四节的 5.0% 直接比**——两者目标不同（天然产物 vs 药物化学分子）。

### 7.3 这 15% 的路线有多可信？（假阳性核查，69 个"可得"前体逐个查）

| 档 | 数量 | 占比 |
|---|---|---|
| 真·同一分子（full InChIKey 命中） | 66 | 95.7%（old 60 + block_full 6） |
| 骨架命中等（构型/取代可能不同） | 3 | 4.3% |
| ★ **假阳性**（前体本身在 ORD 里作过产物 = 其实要合成它） | **0** | **0.0%** |
| 其中 **重原子 ≤ 2 的小分子**（甲醇/乙烷/氯甲烷…） | 12 | 17.4% |

- ✅ **"没编造分子"**：0 个假阳性（实测 0/69）
- ❌ **"路线化学上站不住"**：17.4% 的前体是溶剂级小分子（`CCl`、`CC`、`CO`），
  另有 4.3% 是骨架错配。
  实测例子：**胸苷(Thymidine) ← 碘代胸苷 + 氯甲烷** ← 我们给出的"一步到位"路线。
  这类结果用户看一眼就会不相信这个功能。

### 7.4 建议

1. **现在**：做**只读影子接入**（可回退、不动主流程），让用户拿到真实反馈；
2. **先做②**（逆模板质量）之后，再谈正式接入。

影子接入必须做到 4 件事：
- `D:\TCMAI` 保持只读，逆合成放进 `chemreact-staging`，用 `sys.path` 引；
- tkinter 里**必须后台线程 + 队列**（单分子 `disconnections()` 实测 0.2~9 秒，同步跑会卡死窗口）；
- 结果**过滤**：重原子 ≤ 6 的前体、骨架命中的前体，默认丢掉；
- UI 上明确标 **"实验性"**，不跟现有功能混在一起。

工具：`tools/bench_natural_products.py`、`tools/verify_retro_false_positive.py`、
`tools/recon_tcmai_integration.py`、`tools/probe_tcmdb_schema.py`。
