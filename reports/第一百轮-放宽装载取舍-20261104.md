# 第 100 轮：放宽模板装载的取舍实测（recall / 排序 / 耗时）

日期：2026-11-04
样本：`tools/bench_topk.py --n 3000`（同一 3,000 条测试反应，seed 20261014，模型/条件固定煎煮）。

## 0. 一句话

放宽 mined 模板装载能把**候选召回从 92.47% 提到 95.27%（+2.8 pp）**，但**top-5 从 67.67% 掉到 56.97%（−10.7 pp）**、耗时 **3.7 倍**（261 s → 975 s）。**默认值不改**：这是「多给候选」和「排得准」之间的直接冲突，瓶颈在排序，不在候选。

## 1. 三档对照（全部实测）

| 配置 | recall_any | top-1 | top-5 | top-10 | MRR | 平均候选 | 耗时 |
|---|---|---|---|---|---|---|---|
| 默认（min_support=10, limit 20000, cap 32） | 92.47% | 42.67% | 67.67% | 80.03% | 0.5465 | 21.3 | 261 s |
| 放宽装载（2,300 万→ 装载全量；cap 仍 32） | 87.10% | 40.20% | 56.97% | 65.47% | 0.4903 | 40.2 | 964 s |
| 放宽装载 + cap 128 | **95.27%** | 40.20% | 56.97% | 65.47% | 0.4922 | 47.0 | 975 s |

## 2. 怎么读这张表

1. **只放宽装载、不放宽 cap，召回反而掉 5 pp**（92.47 → 87.10）。原因：每对产物仍只取前 32 条，新模板把原来能上榜的产物挤下去了 —— 这是「容量守恒」的直接证据。
2. **把 cap 放到 128，召回才真正涨到 95.27%**（+2.8 pp，相对 3,000 条样本约 +84 条命中）。
3. **排序全面变差**：top-5 掉 10.7 pp、top-10 掉 14.6 pp，但 top-1 只掉 2.5 pp。说明新增的命中大多落在 **第 6~10 位之后**，而发射序把「新模板的产物」排在后面反而把老命中挤出前 5。
4. **耗时 3.7 倍**（261 → 975 s / 3,000 条）。全量 50,016 条按此推算约 1.8 小时（默认约 30 分钟）。

## 3. 结论

- 第九十九轮说的「缺产物主因是装载截断」**成立**：cap 放宽后召回确实上去了。
- 但**直接把默认值改成放宽档是不划算的**：召回 +2.8 pp，代价是 top-5 −10.7 pp 和 3.7 倍耗时。
- 真正该做的是**排序**：让新增命中从「第 6~10 位」挪进前 5，而不是靠扩大候选池。第 96 轮已证明发射序 > scorer；目前没有更好的排序信号（support / extent / curated 全部实测无效，见第 95、97 轮）。

## 4. 建议

1. **默认不动**（保持 min_support=10、cap 32）。
2. 需要一个「高召回模式」时，用 `--mined-wide --maxprod 128`（`tools/bench_topk.py` 已支持；生产侧还没有对应开关，要接的话是一行参数）。
3. 排序想继续攻，唯一还没试过的方向是**用产物自身性质做先验**（分子量/极性/是否含金属），但这属于「反应可行性」范畴，用户已明确不做（AGENTS §11.8）。

## 5. 复现

```powershell
python -I tools\bench_topk.py --n 3000                       # 默认
python -I tools\bench_topk.py --n 3000 --mined-wide           # 放宽装载
python -I tools\bench_topk.py --n 3000 --mined-wide --maxprod 128
```
