## 2. ★ 更大的发现：我把 60% 的数据扔在门外 ★

写诊断脚本一跑，傻眼了：

```
带【已指定】手性中心的底物: 0 / 1500  (0.0%)
未指定但潜在的手性中心总数: 6939
```

**1500 个底物，一个手性中心都没有？** 中药成分不可能这样。
所以不是"没有"，是"我读错了"。

查 `tcm.db` 的表结构：

```
compounds 表列: ingredient_id, name_en, alias, formula,
                smiles, isomeric_smiles, inchi_key, ...
                        ^^^^^^^^^^^^^^^^  ← 一直没读这一列
```

统计：

| | |
|---|---|
| `compounds` 总行数 | 31,646 |
| **`isomeric_smiles` 含手性标记 `@`** | **19,043（60.2%）** |
| 含双键构型 `/` | 5,762 |
| 两列内容不同 | 21,376 |

**我的 `SELECT c.smiles` 一直在读那个没有立体信息的列。**

### 修法

`sources/herb.py` 和 `rules/schema.py` 两处都改成**优先 `isomeric_smiles`，取不到再退回 `smiles`**。

### 修完的效果

| | 修前 | 修后 |
|---|---|---|
| 带已指定手性中心的底物 | **0 / 1500** | **875 / 1500（58.3%）** |
| 已指定手性中心总数 | 0 | **5,992** |
| 未指定但潜在的手性中心 | 6,939 | 947 |

**跟数据库里 60% 的比例完全对上了。** 从"一个手性中心都没有"变成"58% 的底物带手性"。

## 3. 第四道闸门：`rules/stereo.py`

### 判据（这是关键）

一条规则的作用范围由 SMARTS 里**带原子映射号**的原子界定。

| 手性中心的位置 | 反应会不会动它 | 手性消失算不算错 |
|---|---|---|
| **在作用范围内** | 会 | **正确的化学**（例：羟基氧化把 CHOH 变 C=O，那个碳必然不再手性） |
| **在作用范围外** | 不该动 | **是 bug**（RDKit/rdchiral 应当原样带过去） |

**所以这个闸门只报第二种。** 第一种是化学，不是错。

## 4. ★★ 最重要的教训：验证工具必须和运行时用同一个引擎 ★★

第一版闸门我用 `AllChem.ReactionFromSmarts`（rdkit）跑，报了 **12 条规则**丢手性。

修掉一个"水解把分子断成两片、我拿单片跟整个底物比"的假阳性后，降到 **4 条**。

**但 4 条还是不对。** 手工复验同一个底物：

```
底物 CC1=CC[C@@H](CC1)C(=O)C   手性中心在环外的碳(4)
规则「双键加氢」作用范围 = 环上的 C=C(原子 1,2)  → 手性中心(4) 是旁观者

  rdkit    → 产物手性 0   ← 看起来"丢了"
  rdchiral → 产物数 0（直接拒绝），或产物手性 1（保留）
```

**原因：本项目的引擎对单反应物规则【强制走 rdchiral】。
我拿 rdkit 去验，等于在检查一条引擎根本不走的路——全是假阳性。**

改成 rdchiral 之后：

| 版本 | 报告的问题规则 |
|---|---|
| rdkit + 逐片段比 | 12 条 |
| rdkit + 片段合计 | 4 条 |
| **rdchiral + 片段合计** | **1 条** |

> **验证工具必须和运行时用同一个引擎，否则测的不是同一个东西。**
> 这个坑很隐蔽：rdkit 和 rdchiral 都能"跑通"，但结果不同，
> 而错的那一方看起来更宽松、更容易报"问题"。

剩下的 1 条（`脱水`，2/236 = 0.8%）手工复验时发现我的旁观者判定在某类 SMARTS 上有偏差
（`模板原子数=0` 却仍被标记）。**如实记为待人工复核，不当作已确认的缺陷。**
