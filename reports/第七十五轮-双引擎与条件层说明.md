# 第七十五轮 · 双引擎与条件层说明（重要）

> 起因：B 的 6 个 `condition_profile` 已落地，但用肉桂酸实跑时，
> 实时预测没有产出“肉桂酸型脱羧 → 苯乙烯”，产物全部来自 `mined_mono`。
> 这不是 profile 写错，而是**实时路径与规则层不是同一个引擎**。

## 一、两条路径（实测）

### 实时 UI / `chemreact.py predict`

```
chemreact.py
  → query_base.RunSpec
  → SmartReactEngine（mined_extra / mined_mono 模板）
  → 产物 rule_name = mined_*（generic）
  → 条件表 cond_activation() 只覆盖 37 个命名反应类
```

实测：肉桂酸 `OC(=O)/C=C/c1ccccc1` 在「煎煮」下
（`out/20261017-210000_smiles.csv`）：

* 产物 8 个，`rule_name` **全部是 `mined_mono`**；
* 没有 `C=Cc1ccccc1`（苯乙烯），也没有 `decarboxylation_cinnamic_001`；
* `条件模型（D2）：0/8 条出处带可行性标记`；
* 50,939 产物的「羚角钩藤汤」实跑同样是 `0/50939` 条条件标记。

原因：mined_extra / mined_mono 是**无反应类标签**的通用模板；
条件表没有对应类，`cond_activation()` 只能“无数据放行”。

### 规则层 / `core.engine` / `api.predict`

```
api.predict
  → core.engine.Engine
  → rules/rules.json 的 64 条 curated 规则
  → active_rules() 使用 6 个新 profile
```

实测：

* `test_conditions.py`：20/0；
* `test_condition_gate.py`：通过；
* `run_regression_suite.py --fast`：6/0；
* 肉桂酸规则单独 `RunReactants` 能产出苯乙烯 + CO2。

## 二、B 试点已落地（2026-10-17）

实时引擎已加 `use_curated_templates=True` 试点：

* `SmartReactEngine` 加载 6 条 curated 规则（双底物 2 / 单底物 4）；
* 规则带 `reaction_name`（rule id），条件表用 6 个新 profile；
* `co_substrate_pool`（乙醇/甲醇/葡萄糖/甲硫醇/半胱氨酸）按溶剂自动补共底物；
* `chemreact.py` 实时路径显式打开；评测脚本默认仍为 False，旧基线不变。

端到端实测：

* 肉桂酸 + 煎煮：11 个产物（8 个 mined 无数据放行 + 3 个 curated 窗口内），
  其中 `C=Cc1ccccc1`（苯乙烯）+ `O=C=O` 的
  `rule_name=decarboxylation_cinnamic_001`，`activation=1.0`；
* 苯甲醛 + 醇提：产出 `CCOC(O)c1ccccc1` 等半缩醛，
  `rule_name=condensation_hemiacetal_001`；
* 苯甲醛 + 室温浸泡：产出甲硫醇/半胱氨酸硫代半缩醛；
* 甘草 limit=1 + 醇提：9 个产物、3.5 s，无崩溃。

## 二b、C 试点：top mined per-template 条件

37 类映射不可行：10k 条 mined 模板对 9,770 条已知类模板，
反应中心签名 `exact=0`，RDKit 反应指纹最高相似度仅 0.05–0.13。
因此改用**直接从 ORD 记录给 top mined 模板建 per-template 条件窗口**：

* 按 support 取 Top100 模板，对 20k ORD 等距样本试跑；
* **99/100** 模板至少一次产物匹配；
* 已把 **Top100** 接入实时引擎（`mined_top_001..100`），
  其中 65 条双底物、34 条单底物；
* 实测硝基还原模板（Top1）：对硝基甲苯 → 对甲苯胺，
  `rule_name=mined_top_001`，`activation=1.0`；
* Top100 覆盖总 support 的约 **17.1%**。

这证明 C 可以走“per-template 条件窗口”，不需要先把 mined 模板硬塞进 37 类。
剩余是扩大 TopN（Top100/500）并观察实时产物量与耗时。

## 三、结论

**6 条 curated 规则的条件缺口已在实时路径补上；但 mined_extra/mono
仍然没有反应类标签，通用 mined 产物依旧“无数据放行”。**

所以：

* 6 条 curated 规则的 profile 与实时模板已生效；
* 通用 mined 产物的条件缺口（`0/50939` 的主体）仍在；
* 这是“给全部 mined 模板补反应类”（C）才能根治的问题。

## 四、可选方案

| 方案 | 做法 | 状态/代价 |
|---|---|---|
| A 保持双引擎 | 规则层做审计/验证，实时继续 mined | 不推荐，实时仍缺条件 |
| B 规则层并入实时（试点） | 6 条 curated 模板带 reaction_name 接入 SmartReactEngine | **已落地**；需继续观察产物量/去重 |
| C 给 mined 模板打反应类 | 从 ORD 元数据给 mined 模板补 reaction_name，扩展 37 类条件表 | 未做；数据工程量大，但从根上补实时条件缺口 |

## 五、建议

B 试点已完成。下一步评估 **C**（全量 mined 模板补反应类），
这是把 `0/50939` 条件标记真正降下来的唯一根治路径。
