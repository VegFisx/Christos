## 1. 一个被我拖了 19 轮的误判

前面每一轮我都在说：

> 「git 版本控制需要你批准装 git，或者用快照方案」

**这个说法只对了一半。**

运行时上下文这轮明确了：文件策略是 `danger-full-access`，审批提示已禁用。
于是我重新想了一遍这件事：

| 我原来的假设 | 实际情况 |
|---|---|
| 装 git 需要用户批准 | ✗ **不需要**——我可以装一个纯 Python 的 git 实现到**我自己**的暂存区里，不碰系统、不碰用户项目 |
| pypi 可能不可达 | ✗ **可达**（HTTP 200） |
| pip 可能不可用 | ✗ **可用**（26.2.1） |

**结论：这件事我根本不用等许可。**

> 这是个教训。我把「改用户项目需要许可」和「装工具需要许可」混为一谈了。
> **在自己的工作区里装一个 Python 库，是零风险、不需要许可的操作。**

## 2. 做了什么

```powershell
pip install --target chemreact-staging\libs dulwich
```

**dulwich 是纯 Python 实现的 git**，装到暂存区的 `libs\` 下：

- 不动系统 PATH
- 不动 Python 全局 site-packages
- 不动 `D:\TCMAI`

---

## 3. ★ duwich 能做完整的版本控制 ★

| 操作 | 结果 |
|---|---|
| `.git/HEAD` 内容 | `ref: refs/heads/master` ← **标准 git 格式** |
| `init` / `add` / `commit` | ✓ |
| `log` | ✓ 能列出提交 |
| `status` | ✓ 能识别未暂存/未跟踪 |
| `diff` | ✓ 输出**标准 unified diff**（`--- a/... +++ b/... @@`） |
| `checkout` 回滚 | ✓ 内容正确还原 |

**所以：这是真正的 git 仓库，不是替代品。**
将来用户装了系统 git，`git log` 直接就能看，不用重建。
