## 4. ★ 我引入了一个 bug，然后自己抓住了 ★

加了原子计数缓存之后，**产物数从 455 掉到 18**。

根因：

```python
left = _atom_counts_of_smiles(sub.smiles)   # ← 拿到缓存里的那个 dict
for formula, n in (rule.get("co_reagents") or {}).items():
    left[el] = left.get(el, 0.0) + c * v    # ← 原地改了缓存！
```

缓存的 dict 被越加越多 → 守卫判定"配不平" → 把产物全丢了。

> **缓存可以共享，但共享出去的对象绝不能被调用方改。**
> 修法：返回 `dict(hit)` 副本。

**为什么能抓到**：我每次都会对比产物数。455 → 18 太显眼了。

## 5. ★★ 最大的发现：跨进程不可复现 ★★

优化过程中我一直对不上数：同一份代码，有时 455、有时 454、有时 460。

于是做了最直接的判定——**同一脚本，独立进程跑 5 次**：

```
第1次: COUNT 462
第2次: COUNT 461
第3次: COUNT 463
第4次: COUNT 458
第5次: COUNT 458
```

**每次都不一样。**

固定 `PYTHONHASHSEED=0` 后：

```
452 / 452 / 452   ← 完全一致
```

### 根因

```python
# libs/rdchiral/main.py:131
final_outcomes = set()
...
return [list(x) for x in final_outcomes]    # ← set 转 list，顺序随哈希种子变
```

而 `_collect` 里有 `if len(out) >= limit: break` —— **取"前 N 个"**。
于是每个进程截断下来的产物不一样。

### 修法

```python
outcomes = sorted(outcomes)     # 在 _collect 入口排序
```

### 效果

```
修好后，独立进程跑 6 次：
COUNT 461  HASH fd6b5ed9447181b7   ×6   —— 完全一致
```

## 8. 本轮的三条方法论教训

### 教训一：对照实验必须只改一个变量

第一次测加速比，我只关掉了预筛、忘了关缓存 → 测出 1.06×，**严重低估**。
改成四组严格对照后才是真实的 1.67×。

### 教训二：缓存共享可变状态是个陷阱

返回缓存的 dict 之后，调用方的原地修改会污染它。
**表现是产物数从 455 掉到 18** —— 如果不是每次都对比数量，会静默出错。

### 教训三：进程内确定性 ≠ 跨进程确定性

**Python 的字符串哈希默认是随机化的。**
任何依赖 `set` / `dict` 迭代顺序且"取前 N 个"的代码，
都会在不同进程间给出不同结果。

**审计必须在子进程里做。**
