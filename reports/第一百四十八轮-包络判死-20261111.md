# 第一百四十八轮：条件包络判死

> 时间：2026-11-11。承接第一百四十五轮（包络当筛子）与第一百四十七轮（产物级重排序）。

## 0 一句话

条件包络（「这个转化在文献里是不是在这个温时窗口做过的」）无论按模板查还是按反应类型查，
都**不能区分真产物与同批候选**（AUC 0.488 / 0.502）；按「无区分度就删」的预注册判据，
引擎不再调用它，台账不再出这两列。

## 1 为什么会有这个字段

第一百四十五轮想让条件真的影响产物，于是把 ORD 的「模板 × 条件」观测整理成经验包络：

- 温度落在观测区间 `[t_min, t_max]` 内 → 1.0；超出按 `exp(-d/40 °C)` 衰减；
- 时长同法（`exp(-|ln 比值|/1.5)`）；
- 两者都有观测取几何平均；观测数 < 5 视为未知 → 1.0，不罚。

当时测的 AUC 是 0.488（模板级，150 条留出记录），但因为覆盖率只有 1.7%
（中药路径的模板来自另一套挖掘池，逐字匹配不上），所以先按「扩大覆盖再看」处理。

## 2 这一轮做了什么

**① 按反应中心类型重建（`tools/build_envelope_type.py`）**

把逐字模板聚合成「反应中心类型」：成/断键条数 + 反应中心原子的
（元素、形式电荷、度、芳香性、是否成环、氢数）排序元组。

- 输入：`reports/template_conditions.json` 的 80,166 个模板；
- 输出：`reports/envelope_types.json` —— **16,710 个类型**，250,452 条观测
  （最大类型 n = 17,463，中位 1，长尾明显）；
- 未解析模板 4,999 条（SMARTS 解析失败或无成断键）。

**② 让 `condition_fit` 在模板查不到时退回类型查表**（`conditions/envelope.py`）

**③ 修一个让整列恒为 1.0 的 bug**（`core/query_base.py`）

包络原本在引擎 `step()` 末尾给 `Product` 打属性，但台账每一行是**发射当时**就把字段抄进字典的，
事后打属性传不进去 —— 所以甘草 824 行全部是 1.0、说明列还是空的。改为在台账组装处现算
（带 `(模板, 温度, 时长)` 缓存），824 行不重复查表。

**修复后的覆盖率（甘草 824 个产物，煎煮 100 °C / 60 min）**

| 命中层 | 行数 | 占比 |
|---|---|---|
| 模板级 | 22 | 2.7% |
| 类型级 | 246 | 29.9% |
| 合计 | 268 | **32.5%** |
| 无观测（不罚） | 556 | 67.5% |

有 208 行给出了非 1.0 的判读，例如
`fit=0.4807 反应类型：时长 60 min 在观测区间 [20, 20] 外`。

## 3 判据与结果

判据（预注册，写在探针 docstring 里）：**AUC < 0.6 即判死**。

探针 `_diag/probe_envelope_auc.py`：从 `reports/ord_condition_dataset` 取 300 条同时有温度与时长、
且反应物/产物都带原子映射的记录，**每条用它自己的真实条件**跑引擎（不套煎煮），
标签 = 候选是否等于该记录的产物。

结果（`reports/envelope_auc_type_20261111.json`）：

| 指标 | 值 |
|---|---|
| 候选数 / 真产物 | 5,029 / 99 |
| 有观测覆盖的候选 | 726（14.4%） |
| **AUC** | **0.502** |
| 真产物 fit 中位 | 1.000 |
| 假候选 fit 中位 | 1.000 |

即：**有观测和没观测都与「是不是真产物」无关**。

## 4 为什么必然如此

包络回答的是「这类转化通常在哪做」，而同一批候选往往**来自同一类模板**（引擎的一次运行里，
大多数候选共享少数几条模板），于是同一底物下所有候选的包络值几乎相同 —— 一个对整批候选
几乎恒定的量，天然没有排序能力。这与第一百四十五轮的结论（条件不决定产物身份）是同一件事的
第二个侧面。
