## 一、核心思路：兼容层，不是重写

你的项目里有 **7 处**调用 `tcm_analyzer.predict_reactions(...)`：

```
cascade_reactions.py:57     predict_reactions(frontier)
llm_agent.py:415            predict_reactions(uniq)
plot_any_group.py:76        predict_reactions(compounds)
plot_compare.py:69          predict_reactions(uniq)
run_admet_products_all.py   predict_reactions(compounds)
batch_pairs.py:250          predict_reactions(compounds)
verify_rules.py:68          predict_reactions(uniq)
```

以及另外三个入口：

```
cascade_reactions.py:28     get_reactions()
coconut_analyzer.py:93      reaction_rules.REACTION_RULES
llm_agent.py:42             cascade_reactions.find_final_products(...)
```

**如果直接换实现，这 10 处全要改。**

**兼容层的做法：保留公开 API 与返回结构，只把内部换成新引擎 → 所有调用方一行都不用改。**

```

```


**`get_reactions()`** → `{id: {name, rxn, desc, irreversible, smarts, category, status}}`

## 四、顺带修掉的行为差异（需要你知道）

| 差异 | 旧行为 | 新行为 | 影响 |
|---|---|---|---|
| **小分子产物** | `_valid_product` 直接删（MW<100 或重原子<10）——苯甲酸（9 重原子）被误杀 | **保留并标记 `is_byproduct=True`** | 产物数量会变多；想要旧行为传 `legacy_filter=True` |
| 反应引擎 | rdkit 原生 `RunReactants` | 单反应物走 rdchiral、双反应物走 rdkit | 环内断键不再复制原子 |
| 规则数 | 23 | **63** | 产物数量增加 |
| 条件 | 无 | 增加了条件激活（默认煎煮） | 产物集合随工艺变化 |
| 原子守恒 | 未校验 | 运行时守卫，配不平的产物当场丢弃 | 不会再输出化学上错的分子 |

**最后一条要特别说**：新版会**改变产物列表的内容**。

拿你项目里的旧引擎实测（甘草+附子+干姜，各 20 个成分）：

```
旧引擎              344 个去重产物
新引擎（煎煮条件）    455 个
新引擎（全规则激活）  620 个

同口径：两边都有 180 / 只有旧引擎 164 / 只有新引擎 440
```

**且已证明没有回归**：SMARTS 没改过的规则，放大产物上限后「只有旧引擎」归零
—— 新引擎产出的是**超集**（见 `新旧引擎正面对比.md`）。

> 更详细的影响分解见该文档；**不要把另一个数字「44.6%」当成整体影响**——
> 那是只统计 10 条改过 SMARTS 的规则的旧口径，已被低估。

## 七、预演过程中暴露的两个我的问题

### 问题一：生成代码时漏转义

预演脚本用 f-string 生成驱动代码，**漏转义了一个 `{len(ps)}`**，
被外层提前求值 → `NameError`。

> 教训：**用 f-string 生成代码是脆的**，花括号必须全转义。

### 问题二：引擎放置路径算错一级

第一版把引擎放在副本根目录，而替代模块按 `TCMAI/_chemreact` 去找 → 找不到。

修的时候顺带把**真实搬运的布局定下来了**：放进 `src/chemreact/`，
这样回滚只需"删一个目录 + 还原一个文件"。

> 这正是预演的价值：**路径这种问题，在副本上撞比在你项目里撞好得多。**
