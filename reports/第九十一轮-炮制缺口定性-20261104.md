# 第九十一轮：炮制 4 条缺口的定性（2026-11-04）

## 0. 一句话

6 个炮制案例里，**3 条现在完整一致**（Rb1、乌头碱、槟榔碱），另外 3 条（CATR、JNB、THSG）停在分子式级——**原因是本地库没有对应结构，不是引擎算错**。
过程中挖出两个真 bug：验证脚本没把炮制规则喂给引擎、结构去重把规则归属丢了。

## 1. 你问的「先定性」，四条逐条结论

| 缺口 | 定性 | 证据 |
|---|---|---|
| 槟榔碱 → 去甲槟榔碱（原判「产物对、反应族错」） | **两个 bug，已修**，现在完整一致 | 见 §2、§3 |
| CATR → ATR 骨架（分子式级） | **数据缺口**：库里 `C30H46O16S2` **0 条** | `reports/paozhi_paths_20261104.json` |
| JNB → 内酯/环氧开环酸（分子式级） | **数据缺口**：`C20H28O5` 库里有 **20 个同分异构**，无法唯一定位 | 同上 |
| THSG → 苷元（分子式级） | **数据缺口**：`C14H12O4` 有 **20 个同分异构**，没有精确命名的四羟基二苯乙烯 | 同上 |

## 2. 真 bug ①：验证脚本从来没让炮制规则跑起来

`SmartReactEngine._load_curated_templates()` 里有一句：

```python
if self.curated_rule_ids is None and r.get("paozhi_only"):
    continue
```

意思是**不显式传 `curated_rule_ids`，一条 `paozhi_only` 规则都不会加载**。生产路径
`integration/tcmai_bridge/chemreact.py:1037-1038` 传了 `curated_rule_ids=_paozhi_ids`，
而我的验证脚本 `tools/validate_literature_paths.py::run_once` 只传了
`use_curated_templates=True` —— 于是 `demethylation_n_001` 一次都没跑过，
槟榔碱那条被判成「产物对、反应族错」。

修法：`run_once` 里按条件名分流。炮制档传 `rules/paozhi_evidence.json` 的 11 条 id +
`use_base_templates=False`，与生产严格模式完全对齐；煎煮档保持原样（87 轮的 5 个案例数字逐条不变，已复跑确认）。

修完实测（`Arecoline` / 炮制·炒焦，2.6 s，7 跳）：

```
C=O                        CH2O       rule=demethylation_n_001
[H]N1CCC=C(C(=O)OC)C1      C7H11NO2   rule=demethylation_n_001
COC(=O)C1=CCCNC1           C7H11NO2   rule=demethylation_n_001   ← 去甲槟榔碱
```

## 3. 真 bug ②：结构去重把规则归属吃掉了

`step()` 用 `seen` 按结构去重，**先到的那条规则占住名字**。实测：去甲槟榔碱先被 `mined_mono`
给出，`demethylation_n_001` 那一份被丢掉 —— 化学是对的，台账里只看到 `mined_mono`。
文献对照按反应族判断时，这就会被读成「反应族错」。

修法：`Product` 新增 `also_rules`（逗号分隔），去重命中时把后到的规则补记进去；
台账 `PATH_FIELDS` 同步加一列；`reaction_paths.Hop` 加 `alt_rules`；
`validate_paozhi_paths.family_ok()` 改为对「主规则 + 备选规则」取并集判断。

## 4. 顺手把槟榔碱那条从分子式级提到结构级

库里其实有 **Guvacoline = `HBIN028561`**（`C7H11NO2` / `DYPLDWLIOGXSSE-UHFFFAOYSA-N`），
所以这条不必停在分子式。把 CASE 的目标从 `("formula", "C7H11NO2")` 改成
`("key", "HBIN028561")` 后，判定从 `formula_only` 升到 `consistent`。
